# PR のレビュー

対象: $ARGUMENTS

GitHub には何も書き込まない。コメント、レビュー、approve、ラベル変更のいずれも行わない (`gh pr comment`、`gh pr review`、書き込み系の `gh api` など)。指摘は文案として返し、投稿するかどうかはユーザーが決める。投稿用のコマンド例も示さない。

## 1. 図の形式を決める

引数に mermaid、excalidraw、none のいずれかがあればそれに従う。なければ、作業を始める前に AskUserQuestion で聞く。

- なし
- mermaid: レビュー文書に埋め込む
- excalidraw: ローカルで説明するときに使う

## 2. PR を読む

- `gh pr view` で説明と、既存のコメント (`--comments`) を読む。既に指摘されていることは繰り返さない。
- `gh pr diff` で差分を取る。
- `gh pr checkout` で手元に取り込み、差分の周辺のコードも読む。作業ツリーに commit されていない変更があるときは checkout せず、どうするかユーザーに聞く。

## 3. 理解用の文書を保存する

`tmp/doc/pr-review/{PR 番号}.md` に次を書く。一度作ったら更新しない。

1. 変更の概要。2-3 文で書く。
2. 語彙テーブル。列は「語彙」「日本語訳」「内容」とする。クラス名、変数名、設定キーなど、差分を読むのに必要な語を載せる。
3. 主要な処理のシーケンス図。mermaid を選んだときだけ書く。

excalidraw を選んだときは、excalidraw スキルで同じシーケンス図を作る。

## 4. レビューする

実装者に迎合しない。保守性、性能、既存の動作の変化、実装者が見落としていそうなことを批判的に確認する。指摘がなければ、ないと書く。

指摘は重要度の高い順に並べ、1件ごとに次の項目を埋める。

- 重要度: 高、中、低のいずれか
- 場所: `path:line`
- 問題: 何が起きるか。具体的な入力や状態を挙げる
- 提案: どう直すか
- コメント文案: PR にそのまま貼れる文章

## 5. 返答

保存したファイルのパス、変更の概要、4 の指摘一覧を返す。良い点を並べる節は作らない。
